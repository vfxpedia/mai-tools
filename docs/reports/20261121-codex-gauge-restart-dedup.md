# 재시작 뒤 중복 계기판

## 확인한 원인과 한계

14:25:40~14:25:42에 기존 watch가 살아 있는 상태로 같은 세션의 새 watch 세 개가 별도 셸에서 시작됐다. analyst의 새 창은 팀장이 먼저 닫았고, runner와 verifier에는 기존 이름표 창과 이름표 없는 새 창이 함께 있었다. daemon의 `startup-command-delivery`와 PID 시작 시각으로 확인했다.

해당 시각 collector 로그의 `attached`와 `restoreAccepted`는 비어 있었다. 추가 실행 명령은 collector의 명령과 달리 `--base`가 없었다. 따라서 이 실행들을 collector가 만들었다고 단정하지 않는다. 최초 호출자의 구체적인 설정이나 조작은 로그로 확정하지 못했다.

기존 collector는 화면 배치와 등록 파일만으로 새 분할 여부를 정했다. 기존 watch가 살아 있어도 복원 중 배치에 잠시 안 보이는 경우를 시험으로 만들자 새 split을 요청했다. 이미 생긴 중복 프로세스를 대조하는 경로도 없었다. 이 두 빈틈을 수정했다.

## 수정과 안전 경계

- 기존 watch 프로세스가 있으면 복원 중 배치에서 빠져 있어도 새 창을 만들지 않는다.
- 동일 세션과 상태 폴더의 정확한 설치본 watch 두 개가 같은 탭과 작업 공간에 있는지 확인한다.
- 고유한 `mai-codex-gauge <session ID>` 이름표가 있는 기존 창을 보존한다.
- 이름표 없는 중복만 닫는다. 실행 파일, 스크립트, 세션, pane key, 핸들이 모두 증명돼야 한다.
- 닫기 직전에 pane incarnation과 PID 시작 시각을 다시 대조한다. PID가 바뀌거나 사라지면 닫지 않는다.
- 일반 셸, 에이전트, 다른 세션, 다른 작업 공간, 임의 이름표 창, 화면만 비슷한 창은 대상이 아니다.
- `/proc`의 계기판 식별 자료만 반환한다. 환경 전체나 프롬프트, 인증 파일은 보고하거나 저장하지 않는다.
- `duplicatesClosed`와 `duplicateFailures`를 서비스 로그로 남긴다.

## 시험과 운영 확인

신규 반례를 먼저 실패시킨 뒤 수정했다. 제품 전체 `npm test`: 135개, 통과 128개, 실패 0개, 플랫폼 조건에 따른 skip 7개. Linux 프로세스 판독 시험은 Linux에서만 실행한다.

runner 중복은 정확한 화면과 PID를 확인해 닫았다. verifier 중복은 수정된 서비스가 14:39:19에 자동으로 닫았고, `duplicatesClosed` 한 건과 `duplicateFailures: []`를 기록했다. 계기판 동기 서비스만 재시작했다. 에이전트와 GPU 작업은 종료하거나 재개하지 않았다.

운영 프로세스를 다시 세어 여섯 세션 모두 watch 하나씩임을 확인했다. 화면에 열린 다섯 세션은 기존 이름표 창을 그대로 보존했다. runner와 verifier 화면에서 중간 중복 창이 사라지고 기존 아래 창이 남은 것을 확인했다.

150px는 기존 아래 창의 배치를 보존하는 방식이다. 현재 Orca 공개 split CLI에는 높이 인자가 없다. 신규 창을 자동으로 정확히 150px로 만드는 기능이 생겼다고 주장하지 않는다. 전체 Orca 재시작은 진행 중인 다른 작업을 보호하기 위해 이번에 실행하지 않았다. 재시작 경계는 격리 회귀시험과 실제 중복 상태 복구로 검증했다.

## 되돌리기

설치기는 변경 전 바이트와 manifest를 Codex 홈의 `mai-codex-gauge-backups`에 보존한다. 해당 manifest를 `setup.mjs rollback --manifest <절대 경로>`에 주고 계기판 동기 서비스만 재시작하면 된다. 닫은 중복 창의 작업 데이터는 없으며 기존 정본 계기판과 에이전트 대화는 유지했다.
