# 03 구성 층

## 1. 한눈에

| 층 | 하는 일 | 사는 곳 | ORBIT | NEBULA | UNIVERSE |
|---|---|---|---|---|---|
| 모으기 | 열린 탭 · 창 · 탭 묶음, 방문 기록, 북마크, 붙인 생각, 음성, 「공유하기」로 온 것 | 브라우저 확장, 휴대폰 화면 | 열린 탭 · 창 · 묶음 | 나머지 전부 | (NEBULA 에서 받음) |
| 기억 | 페이지 · 방문 · 관계 · 카드 상태 · 작업 공간 · 휴지통 | 각 기기 (확장 저장소와 동반 앱의 파일), 사용자가 고른 동기화할 곳 | 페이지 · 작업 공간 · 휴지통 | 방문 · 관계 · 생각 · 카드 상태 | 별 · 별자리 · 공개 범위 |
| 이해 | 분류, 중복, 의도 짐작, 관계 추론, 요약, 메모리 실측 | 확장 (규칙), 동반 앱 (실측 · PC 안 모델), 모델 연결부 | 분류 · 중복 · 의도 · 실측 (동반 앱이 있을 때) | 관계 · 요약 · 주간 보고 | 같은 별 찾기 |

원칙: **아래 층은 위 층 없이 돌고, 단계는 다음 단계 없이 돈다.** ORBIT 만 깔아도 모으기 · 기억 · 이해 · 보여 주기가 다 된다 (메모리 실측만 동반 앱이 있어야 한다). NEBULA 를 켜면 같은 층에 일이 더해진다.

## 2. 구성 요소

| 요소 | 무엇 | 없을 때 |
|---|---|---|
| 확장 | 브라우저 안에서 모으고, 탭을 열고 · 재우고 · 닫고 · 옮기고, 화면을 그린다 | 제품이 없다 (필수) |
| 동반 앱 | PC 에서 메모리를 실제로 재고, PC 안 모델을 돌리고, 에이전트 창구와 휴대폰 화면을 연다 | 메모리 숫자 대신 탭 수만, 에이전트 창구 없음, 휴대폰은 동기화할 곳을 통해서만 |
| 동기화할 곳 | Google Drive (기본) · 내 서버 · 구독 중 하나 | 기기마다 따로 논다 |
| 휴대폰 화면 | 동반 앱이나 내 서버가 띄우는 웹 화면, 「공유하기」 받기 (웹 화면이 받으려면 Android 에 설치한 웹 앱의 공유 대상 기능이 필요하고, iOS 는 지원하지 않는 것으로 안다, 미확인) | 휴대폰에서 못 본다 |
| 모델 연결부 | 요약 · 분류 · 관계 추론을 맡길 곳을 고른다 | 규칙만 쓴다 (무료판 기본) |

지금 2 판과 비교하면: 2 판의 「서버」 (`mai_tabs/server.py`) 가 동반 앱의 씨앗이다. 2 판은 화면도 서버가 띄우지만, 다음 판에서는 첫 화면을 확장 (사이드 패널) 으로 옮기고, 서버는 실측 · 모델 · 에이전트 창구 · 휴대폰 화면을 맡는다.

## 3. 자료의 흐름

1. 확장이 탭 · 창 · 묶음의 변화를 받는다 (탭이 열림 · 바뀜 · 닫힘 · 옮겨짐). 2 판도 변하면 2 초 뒤에 보내지만 매번 전체를 보낸다. 다음 판은 **바뀐 부분만** 보낸다. 놓친 변화를 맞추는 주기적인 전체 전송은 남기되 간격을 늘린다
2. 주소를 깨끗하게 한다: 비밀이 든 파라미터를 빼고, 거르는 사이트 (로그인 · 메일 · 은행 등) 는 아예 남기지 않는다 (2 판의 규칙을 이어 씀)
3. 기억 층에 쓴다: 페이지 (한 페이지는 하나), 방문 (언제 · 어디서 넘어왔나), 관계
4. 이해 층이 붙는다: 분류 · 중복 · 의도는 바로, 관계 추론 · 요약은 한가할 때
5. 보여 주기 층이 읽는다. 제안은 이해 층이 만들고, 사용자가 누를 때만 확장이 동작한다
6. 동기화가 켜져 있으면 바뀐 부분만 동기화할 곳으로 보낸다 (구독이면 기기에서 암호화한 뒤)

## 4. 관계를 무엇으로 아나

코드를 지식 그래프로 만드는 도구 graphify 가 관계마다 「원본에 적힌 것」과 「도구가 추론한 것」을 나누듯, 여기서도 관계마다 「관찰」과 「추론」을 나눠 적는다. 관찰은 사실이고, 추론은 틀릴 수 있어 사용자가 고칠 수 있다.

| 관계 | 근거 | 종류 |
|---|---|---|
| 이 탭에서 저 탭이 열렸다 | 탭이 열린 출처 탭 (확장 API 의 `openerTabId`). 탭 id 는 브라우저를 다시 켜면 바뀌므로 그 순간 페이지 id 로 바꿔 적는다 | 관찰 |
| 이 방문에서 저 방문으로 넘어왔다 | 방문 기록의 「넘어온 방문」 (`referringVisitId`). 사용자 0 의 Chrome 기록 파일에서는 방문 37,141 건 중 17,485 건 (47 %) 에 값이 있었다 (2026-10-25 실측, 확장 API 로 같은 값이 오는지는 확인 필요) | 관찰 |
| 같은 창 · 같은 묶음에 함께 있었다 | 창과 묶음, 시각 | 관찰 |
| 연달아 봤다 | 마지막으로 본 시각 | 관찰 |
| 같은 내 프로젝트의 자료다 | 저장소 · 이슈 주소, 사용자가 붙인 묶음 | 관찰 |
| 같은 주제다 | 제목 · 주소 (무료는 규칙과 PC 안 모델, 유료는 모델 연결부) | 추론 |
| 이래서 열었겠다 (의도) | 위 관계와 행동 (머문 시간, 다시 본 횟수) | 추론 |

지난 관계는 나중에 거슬러 모을 수 없다. 게다가 **Chrome 은 방문 기록을 약 90 일만 남긴다** (사용자 0 의 쓰는 프로필에서 가장 오래된 방문이 정확히 90 일 전, 2026-10-25 실측). 그래서 신호 수집은 첫 단계 (A) 부터 하고, NEBULA 를 켠 날부터는 우리 쪽에 쌓아 90 일이 지나도 남게 한다. 처음 켤 때 가져올 수 있는 과거도 최대 90 일 안팎이다.

## 5. 다섯 가지 중립을 지키는 자리

| 중립 | 연결부 | 처음에 붙일 것 | 나중에 |
|---|---|---|---|
| 모델 | 「요약 · 분류 · 관계 추론」을 받는 층. 입력은 제목 · 주소 (본문은 사용자가 고른 탭만), 출력은 정해진 모양 | 규칙, PC 안 모델 (OpenAI 호환 로컬 서버), 클라우드 모델 하나 | 다른 클라우드 모델, 사용자 자기 키. 어느 판에 무엇이 들어가는지는 BM (비공개) |
| 브라우저 | 확장 안의 「브라우저 어댑터」. 탭 · 창 · 묶음 · 재우기 · 방문 기록 · 북마크 | Chrome | 같은 확장으로 Edge · Brave · Whale (사이드 패널 등 지원 범위는 미확인), 나중에 Firefox · Safari (API 가 달라 어댑터를 따로) |
| 기기 | 동기화 어댑터 | Google Drive (기본), 내 서버 (로컬 폴더 + 사설망 안내) | 구독 (종단간 암호화) |
| 에이전트 | 동반 앱이 여는 MCP 도구 (찾기 · 최근 관심 · 페이지 하나 보기) | 제품 담당자 본인의 에이전트 세션 | 사용자가 허락한 어느 에이전트든 |
| 출처 | 「받기」 층. 무엇이 왔든 페이지 · 생각으로 바꾼다 | 브라우저 탭 | 휴대폰 「공유하기」, SNS 에서 본 것 |

## 6. 지켜야 할 경계

- **확장이 아니면 탭을 건드리지 않는다.** 동반 앱 · 휴대폰 · 에이전트는 「해 달라」는 요청만 보낸다. 실제 동작은 확장이 그 순간의 탭을 다시 확인한 뒤에 한다 (2 판에서 검증한 방식)
- **에이전트 창구 (MCP) 는 읽기 전용으로 시작한다.** 에이전트가 탭을 닫거나 기록을 지우는 것은 나중에, 사용자 확인을 거쳐서만. 사용자가 따로 허락한 운영 규칙 (예: 정해진 에이전트가 화면 API 로 탭을 재우는 것) 은 예외이고, 에이전트 창구의 범위가 아니다
- **에이전트에게 나가는 글은 자료이지 지시가 아니다.** 탭 제목과 페이지 내용은 웹사이트가 정한 글이라 에이전트에게 명령을 심는 통로가 될 수 있다. 창구는 결과를 「자료」로 표시해 내보내고, 에이전트 쪽 안내에도 그렇게 적는다
- **기기 사이 명령은 서명하고, 보관함에 있는 주소만 연다.** 동기화할 곳 (예: Drive 폴더) 에 쓸 수 있는 누구나 명령을 넣을 수 있기 때문이다. 확장은 서명이 맞는 명령만 받고, 2 판처럼 보관함에 있는 페이지만 연다
- **방문 기록과 붙인 생각은 기본으로 기기 밖에 나가지 않는다.** 동기화를 켤 때 무엇이 나가는지 따로 보인다
- **ORBIT 은 NEBULA 없이 완결된다.** NEBULA 를 끄면 그때부터 방문 기록 · 관계 · 생각을 더 모으지 않는다. 이미 쌓인 것을 지울지는 끌 때 따로 묻는다. ORBIT 의 기능은 그대로다

## 6a. 자료마다 정본은 한 곳

| 자료 | 정본 | 사본 |
|---|---|---|
| 지금 열린 탭 · 창 · 묶음 | 브라우저 자체 (확장이 그 순간 읽는다) | 기억 층의 마지막 상태 |
| 페이지 · 작업 공간 · 휴지통 · 카드 상태 · 관계 · 생각 | 동반 앱이 있으면 동반 앱의 파일, 없으면 확장 저장소 | 동기화할 곳 (암호화 사본) |
| 메모리 실측 | 동반 앱 | 없음 |

2 판에서도 서버 (동반 앱의 씨앗) 가 정본이다. **확장 저장소만 쓰는 사용자는 확장을 지우면 자료도 함께 지워진다.** 이것은 「닫아도 잃지 않는다」를 깬다. 그래서 동반 앱이 없는 사용자에게는 동기화를 켜라고 첫 주 안에 권하고, 확장을 지우기 전에 내보내기를 보인다 (지울 때 알림을 받을 수 있는지는 확인 필요).

## 6b. 실패할 때

| 상황 | 동작 |
|---|---|
| 동반 앱이 꺼졌다 | 확장이 확장 저장소에 쌓아 두고, 다시 켜지면 넘긴다. 메모리 숫자는 「동반 앱 꺼짐」으로 표시 |
| 동기화가 충돌했다 | 기기마다 바뀐 기록을 남기고 둘 다 살린다. 같은 칸을 동시에 바꾸면 나중 것을 쓰되 앞의 것을 기록에 남긴다 |
| 동기화할 곳이 꽉 찼다 · 접속이 끊겼다 | 기기는 혼자 계속 돌고, 화면에 「동기화 멈춤」과 이유를 보인다 |
| 확장이 업데이트됐다 | 자료 모양에 판 번호를 두고, 새 판이 옛 판을 읽어 옮긴다. 옮기기 전에 사본을 남긴다 |
| 모델 연결부가 실패했다 | 규칙으로 돌아가고, 다음에 다시 부른다 |

## 7. 정해진 것

- 다섯 층과 단계별 경계 (제품 담당자 10/25 승인)

## 8. 남은 질문 (07 기술 설계에서 정한다)

- 확장 저장소의 한도 (`storage.local` 은 10 MB, `unlimitedStorage` 권한이나 IndexedDB 로 넘을 수 있는 것으로 안다) 안에서 방문 기록과 관계를 감당하는 방식
- 확장을 지울 때 사용자에게 내보내기를 보일 수 있는가
- 방문 기록의 「넘어온 방문」이 확장 API 로 실제로 얼마나 채워져 오는가 (기록 파일에서는 47 %)
- 동반 앱을 어떤 형태로 줄지 (설치 파일, 운영체제별)
- 동기화 자료의 모양 (바뀐 것만 보내기, 충돌 처리)
